# Project 2 (flagship) — On-premises Egyptian support-ticket model

Status: **approved in outline on 2026-10-23; the detailed plan still needs Ahmed's approval** (working agreement §2–§3).
Suggested repo: `masry-support-ticket` (standalone, private until release). Expected time: 2–3 weeks part-time, after Project 1.
Theme shared with Project 1: **Egyptian banking customer support**. The intent list is the ArBanking77 taxonomy.

## Goal

Fine-tune a **small open LLM with QLoRA** that turns an Egyptian-dialect or Franco banking support conversation into a **structured JSON ticket**, and runs on hardware a bank could own.

**Why fine-tune, not prompt a big API:** Egypt's Personal Data Protection Law (Law 151 of 2020) restricts sending personal data abroad. Banks and contact centres (for example Raya CX) need models they can run locally, at low cost and with low latency. Prove with numbers that a prompted small model isn't good enough and the fine-tuned one is.

## Draft ticket schema (finalise in phase 1)

`intent` (an ArBanking77 intent), `summary_msa` (a summary in standard Arabic), `entities` {`amount`, `currency`, `card_type`, `date`, `transaction_ref`}, `urgency` (low / medium / high), `sentiment`, `next_action`, `needs_human` (bool).

## Models

- **Base-model candidates:** `Qwen/Qwen3-4B-Instruct-2507` (Apache-2.0) and `MBZUAI-Paris/Nile-Chat-4B` (built for Egyptian Arabic and Arabizi; check its licence). `Qwen3-1.7B` is for a size ablation. Pick using the baseline evaluation.
- **Teacher, for the training data:** a large open-weights model **whose licence allows training on its outputs**, for example Apache-2.0 Qwen3 through a hosted API. Avoid licences with naming or usage clauses. Record the teacher and its licence in the data card.

## Data

- **No public dataset of Egyptian customer-service conversations exists** (Hub search on 2026-10-23), so the training data is synthetic distillation:
  - generate conversations by combining intent × scenario × Egyptian Arabic script / Franco / mixed English × customer persona;
  - the teacher labels them;
  - filter: schema validation, near-duplicate removal, dialect and length checks, and a **leakage check against the test set**;
  - make sets of 1k, 3k and 6k examples, versioned with DVC, with a data card.

  Ahmed reviews a sample of about 50 training examples for realism.
- **Test set, written by Ahmed:** about 200 conversations (Egyptian Arabic script, Franco, code-switching), with gold labels he writes. It is never generated by the teacher, so the teacher never grades its own outputs. About 50 of these also get Ahmed's own quality ratings, used to check the AI grader.

## Phases

1. Ticket schema and the hand-written test set.
2. Synthetic data generation, filtering and leakage checks (DVC).
3. Baselines: the base model prompted (zero-shot and few-shot) vs the teacher.
4. QLoRA fine-tuning with TRL `SFTTrainer`: chat template, loss on the completion only, 4-bit NF4 quantization. Every run logged in MLflow. Ablations: 1k / 3k / 6k examples, LoRA vs QLoRA, with and without Franco, base-model choice.
5. Evaluation and error analysis (see below).
6. Promotion gate, then release: the model and a GGUF Q4 version on the Hub with a model card; a FastAPI service (llama.cpp or vLLM) and a Gradio demo on Hugging Face Spaces; Docker; CI with schema and parsing tests plus the evaluation script on cached predictions; README with a results table and limitations.

## Evaluation

- Valid JSON %, accuracy per field (entity F1), intent macro-F1.
- Summary faithfulness and completeness, graded by an LLM. Report how often the grader agrees with Ahmed's ratings on the 50-example subset.
- Every metric split by script and dialect (Egyptian Arabic script vs Franco).
- Throughput and response time on a T4 and on CPU (GGUF), and cost per 1,000 tickets vs the API teacher.
- The promotion gate's thresholds (JSON validity, field accuracy close to the teacher's, minimum faithfulness, p95 response time on a T4) are agreed **before** training.

## Learning prerequisites

- Hugging Face LLM course chapter 11 sections 2–5 (chat templates, `SFTTrainer`, LoRA, evaluation).
- PEFT and bitsandbytes docs on QLoRA; TRL `SFTTrainer` docs.

## Risks

- Synthetic data that doesn't sound real: mitigated by Ahmed's hand-written test set and his review of training samples.
- Teacher mistakes passing into training: mitigated by filtering, spot checks and per-field error analysis.
- Invalid JSON: measure it first; consider constrained decoding later.
- T4 memory limits: gradient checkpointing and a capped sequence length.
- Licensing of the teacher's outputs and the base model.
